## Context

executorch-bencher currently has no code beyond a stub `Cargo.toml` and an
empty `src/main.rs`. See `proposal.md` - Why for the motivation. This design
covers the concrete schema, migration structure, and service skeleton needed
to satisfy `specs/benchmark-schema` and `specs/ingestion-service`.

The target production topology (from prior architecture discussion, not
re-litigated here) is:

```text
Benchmark runners on devices
        -> HTTPS
Rust ingestion API (Axum)
        -> PostgreSQL (metadata, results, comparisons)
        -> S3/MinIO (logs, models, inputs, output artifacts)
        -> Rust dashboard backend -> browser dashboard
```

This change builds the PostgreSQL schema and the service skeleton only.

## Goals / Non-Goals

**Goals:**
- Land a complete, normalized PostgreSQL schema (as SQLx migrations) covering
  campaigns, device/source snapshots, artifacts, run configurations, runs,
  metrics, telemetry, and validations.
- Stand up a minimal Axum service that connects to Postgres, runs migrations
  on startup, and exposes a health check, as the foundation later ingestion
  endpoints attach to.
- Establish naming and typing conventions (UUIDv7 primary keys, `timestamptz`,
  `jsonb` for evolving metadata) consistently across all tables so later
  migrations extend rather than fight the schema.
- Provide a self-contained local development and test story: a
  `docker-compose.yml` for running the service by hand, and
  `testcontainers-rs` so `cargo test` provisions its own database without
  manual setup.

**Non-Goals:**
- No actual ingestion endpoints (e.g. "submit a run") or dashboard/query
  endpoints - only the health check route is added in this change.
- No S3/MinIO client integration - `artifacts.storage_uri` is stored as an
  opaque string; nothing in this change writes or reads object storage.
- No TimescaleDB - `run_telemetry` is created as an ordinary Postgres table;
  converting it to a hypertable is deferred until telemetry volume justifies
  it.
- No authentication/authorization on the HTTP service, and no `users` table -
  `benchmark_campaigns.created_by` is an unconstrained `uuid` placeholder
  until a real identity system exists (see Decisions).
- No runner-side code (the processes that would call this API from devices).
- No CI pipeline - `docker-compose.yml` and `testcontainers-rs` make the
  service and tests runnable locally, but wiring a GitHub Actions workflow
  around them is deferred to a separate change.
- No seed data for the `metrics` catalog - it ships as an empty table;
  populating it is deferred to whichever change first records real metric
  values, to avoid guessing metric names now.

## Decisions

### UUIDv7 primary keys generated by the application
All entity tables use `uuid` primary keys rather than serial integers, except
the `metrics` catalog, which uses a `bigint` identity column. Generated UUIDs
use version 7 (time-ordered), not version 4 (random).
- **Why**: UUIDs let runners/collectors generate identifiers client-side
  before a network round trip if needed later, and avoid leaking row counts.
  High-insert-volume tables (`runs`, `run_metrics`, `run_telemetry`) would
  suffer B-tree index fragmentation with random v4 keys; v7's time-ordered
  layout keeps inserts roughly sequential, avoiding that cost. The `metrics`
  catalog is a small, curated, server-managed lookup table where a simple
  identity key is more natural and slightly cheaper to join.
- **Alternative considered**: `bigint identity` everywhere - simpler and
  faster to index, but doesn't support client-side ID generation and was
  rejected to keep the door open for offline/queued collection later.
  UUIDv4 was also considered and rejected once insert volume and index
  locality were weighed against the negligible cost of switching to v7.

### `campaigns.created_by` as an unconstrained placeholder
`benchmark_campaigns.created_by` is a plain `uuid NOT NULL` column with no
foreign key, since this change introduces no `users` table and the project
has no identity/auth system yet.
- **Why**: Inventing a `users` table now would guess at a schema this change
  isn't scoped to design. Keeping the column but leaving it unconstrained
  preserves the intended shape of the data (every campaign has a creator)
  without blocking on unrelated work.
- **Alternative considered**: drop the column until a real identity system
  exists - rejected because every other table in this schema fills in this
  kind of provenance field, and re-adding it later would be a backfill
  problem instead of a one-time deferred decision.

### Local Postgres via `docker-compose.yml`, tests via `testcontainers-rs`
Development runs against a `docker-compose.yml`-provisioned Postgres;
integration tests provision their own ephemeral Postgres through
`testcontainers-rs` rather than assuming a shared running instance.
- **Why**: The migration and service tasks in this change are untestable
  without *some* Postgres to point at, and the repo currently provisions
  none. `testcontainers-rs` makes `cargo test` hermetic and reproducible -
  no developer setup step, no shared state between test runs - consistent
  with the project's emphasis on reproducible results. `docker-compose.yml`
  remains useful separately for manual `cargo run` / `psql` exploration.
  A local Docker daemon was confirmed available in this environment.
- **Alternative considered**: a single long-lived local/CI Postgres reached
  via `DATABASE_URL` - simpler to reason about but pushes a manual setup
  step onto every developer and risks state leaking between test runs;
  rejected in favor of `testcontainers-rs`'s isolation.

### Compile-time query verification with a committed offline cache
Database queries use SQLx's `query!`/`query_as!` macros, checked against a
real schema at compile time, with the resulting `.sqlx` cache committed to
the repository so `SQLX_OFFLINE=true` builds (e.g. without a live database)
still get the same checking.
- **Why**: Compile-time checking catches SQL/type mismatches before runtime,
  and committing the offline cache means builds don't require a live
  database connection just to compile - useful for any environment without
  Docker or a reachable Postgres instance.
- **Alternative considered**: a runtime query builder with no compile-time
  checking - more flexible for dynamic queries but gives up static
  verification for the mostly-static queries this schema needs; rejected in
  favor of the stronger safety net.

### Enumerated run status as a Postgres ENUM type
`run_status` is a native Postgres `ENUM`, not a text column with an
application-level check.
- **Why**: A fixed, small set of outcomes benefits from database-level
  enforcement and compact storage; it directly reflects the fixed vocabulary
  in the spec's run-outcome scenario.
- **Alternative considered**: a `text` column with a `CHECK` constraint -
  more flexible to extend without a migration, but ENUM is preferred here
  since new run outcomes are rare and should be a deliberate schema change.

### Configuration comparability fingerprint computed and stored, not derived at query time
`run_configurations.configuration_hash` is computed once (in the application
layer, from a canonical serialization of all result-affecting fields) and
stored as a column, rather than computed on the fly during comparison
queries.
- **Why**: Storing it lets it be indexed and used directly in `WHERE`/`GROUP
  BY` clauses for "only compare like-for-like" queries, and freezes the
  fingerprint definition at write time so later changes to the hashing
  scheme don't retroactively change historical comparability groupings.
- **Alternative considered**: compute the fingerprint at query time from
  constituent columns - avoids any risk of a stale hash, but makes indexing
  and grouping by comparability much more awkward and couples every query to
  the current hashing logic.

### Metrics as an entity-attribute-value table, not wide columns
`metrics` (catalog) + `run_metrics` (observations) replace a single
wide `runs` table with one column per possible metric.
- **Why**: The set of metrics benchmark tooling reports will grow and vary by
  model/backend; a wide table would need a migration for every new metric
  and would be mostly `NULL`s. This mirrors the schema note in the proposal
  and is standard for this kind of variable measurement data.
- **Alternative considered**: a single `jsonb` metrics blob per run - loses
  the ability to index, aggregate, and type-check individual metric values
  efficiently in Postgres; rejected per the project's "don't put everything
  in JSON" guidance.

### Migrations embedded via SQLx's compile-time migrator
The service runs `sqlx::migrate!()` against the configured database at
startup rather than requiring a separate manual migration step.
- **Why**: Keeps schema version and binary version tied together, and
  matches the spec requirement that the service brings the schema up to date
  before serving traffic.
- **Alternative considered**: a separate `sqlx-cli migrate run` step in
  deployment tooling, decoupled from the service binary - more flexible for
  large deployments wanting a distinct migration stage, but adds an
  operational step this project doesn't need yet; can be introduced later
  without changing the migration files themselves.

### Service skeleton module layout
`src/` is split into `config` (env-based settings), `db` (pool construction
and migration invocation), `http` (Axum router and the health handler), and
`main.rs` (wiring/bootstrap only).
- **Why**: Keeps the startup sequence (config -> db -> router -> serve)
  legible and gives later ingestion-endpoint work an obvious place to land
  (`http`) without touching bootstrap code.

## Risks / Trade-offs

- [Risk] Choosing ENUM for `run_status` makes adding a new run outcome later
  require a migration (`ALTER TYPE ... ADD VALUE`) rather than an application
  change. -> Mitigation: the outcome set (queued/running/succeeded/crashed/
  timed_out/cancelled/invalid_output/infrastructure_error) already covers
  the realistic failure modes described in the source architecture notes;
  ENUM alterations in Postgres are low-risk, non-blocking operations.
- [Risk] Running migrations automatically on every service startup could
  race if multiple service instances start concurrently against the same
  fresh database. -> Mitigation: SQLx's migrator takes a Postgres advisory
  lock during migration, making concurrent startups safe; this change ships
  a single-instance skeleton so the risk is latent, not active.
- [Risk] Storing `configuration_hash` at write time means a bug in the
  hashing logic could produce incorrect comparability groupings that persist
  until corrected. -> Mitigation: this is an accepted trade-off for this
  change; the append-only/immutability requirement means a future fix would
  add a new hash version rather than silently rewrite history, consistent
  with the schema's correction-handling requirement.
- [Risk] No authentication on the ingestion service means anyone who can
  reach it can write data once ingestion endpoints are added in a later
  change. -> Mitigation: out of scope here since no ingestion endpoints
  exist yet; must be addressed before any change that adds a real
  data-accepting endpoint.
- [Risk] `benchmark_campaigns.created_by` has no foreign key, so nothing
  prevents it from referencing a nonexistent or later-repurposed identity.
  -> Mitigation: accepted as a deliberate, documented placeholder; a future
  identity/auth change must add the `users` table and backfill this
  constraint rather than assume it was ever enforced.
- [Risk] `testcontainers-rs` requires a working Docker daemon on any machine
  running `cargo test`, which a plain `cargo test` did not previously need.
  -> Mitigation: confirmed Docker is available in this development
  environment; this becomes a documented prerequisite for contributors, and
  is a known cost of the hermetic-test decision above.
